## Fase B — Diseño de arquitectura Rank/LP persistence

- Modelo `RankSnapshot` (dominio puro, `src/lib/rank-history/types.ts`): `puuid`, `queueType` (`RANKED_SOLO_5x5`), `tier`/`rank`/`leaguePoints` opcionales (honesto para no clasificados), `wins`/`losses`, `observedAt`, `source` (`overview`|`cron`).
- Orden de rango real tier→division→LP en `rank-order.ts` (`compareRank`), separado deliberadamente de `compareTierDivision` (tier→division, sin LP) usado solo para detectar transiciones reales — una fluctuación de LP dentro de la misma división nunca se reporta como cambio de rango.
- Política de deduplicación (`dedupe.ts`): inserta solo si es la primera observación, si tier/rank/LP/wins/losses cambiaron, o si pasaron ≥6h (`HEARTBEAT_MS`) desde el último snapshot — evita miles de filas casi idénticas sin perder prueba de seguimiento activo.
- Patrón repositorio/adaptador: `types.ts` (dominio) → `d1-repository.ts` (el único fichero que conoce nombres de tabla/columnas D1) → endpoints HTTP (orquestación). Sin SQL fuera del adaptador, sin lógica Riot duplicada.
- Migración SQL (`migrations/0001_rank_snapshots.sql`) con cabecera documentando el proceso humano de 3 pasos (crear D1 → bind `DB` → migrar `--remote`) — **no se ejecuta sola**, requiere aprovisionamiento manual explícito (bloqueador de infraestructura, reportado honestamente).
- Endpoint de lectura pública `GET /api/riot/rank-history` (solo lectura, se degrada a `available:false` sin storage/PUUID/error — nunca un 500) y endpoint de escritura `POST /api/riot/rank-snapshot-cron` (gateado por `RANK_SNAPSHOT_CRON_SECRET` vía `Authorization: Bearer`, nunca acepta PUUID del cliente).
- Escritura desde `/api/riot/overview` vía `waitUntil()` (cero latencia añadida a la respuesta pública), reutilizando `resolveSelfAccountPuuid` (envoltorio nuevo sobre la cuenta ya cacheada 24h) — en el caso normal, 0 llamadas Riot nuevas para la observación.
